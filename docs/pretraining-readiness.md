# Pre-training integration and release readiness

Audit date 2026-11-19. Baseline commit `d77c927`, ICT package 0.1.0. The repository planning file is `PLANS.md`. The audit used the existing editable Windows environment, synthetic fixtures, and read-only checks of selected local assets. Existing AI Hub files and experiment artifacts were preserved.

| Status | Scope |
| --- | --- |
| **READY** | CPU preprocessing and data diagnostics, detector and product interface fixtures, inspection CLI, ASGI API, SQLite history and recovery, dashboard JavaScript, local artifact handling, and detector/product architecture forward passes in the tested environment. |
| **BLOCKED** | Full GPU detector training requires a reviewed and sealed full cohort, a frozen selection policy, a provisioned target, and an approved hardware pilot. Product fitting requires a reviewed sealed revision, matching Train state, verified branch coverage, and an explicitly approved pilot on the intended host. |
| **UNVERIFIED** | Full-size GPU runs, trained product checkpoints, real checkpoint serving in this audit, physical sensor acquisition, production latency and calibration, and independently collected real-world detection performance. |

| Area | Implemented contract and verification |
| --- | --- |

## Checkpoints, preprocessing and reproducibility

- Pin the ICT code revision, backend builds, driver, device, operating system, seed, model YAML, class/label policy, split and annotation digests, input resolution, precision, batch and workers. Save the resolved config, checkpoint selection rule and full training/evaluation artifacts together. Content hashes establish identity. Keep provenance and trust decisions with the artifacts.
- Pretrained transfer verifies the local file’s SHA-256, source architecture, consuming library version and exact tensor layout. The staged official YOLO, Faster R-CNN and RT-DETR files matched all three SHA-256 values in the smoke profiles. Those profiles pin the local TorchVision CPU build. Pin the actual compatible build when preparing a GPU profile. YOLO native checkpoint loading requires trusted pickle. Faster R-CNN and RT-DETR use `ict-torch-state-v1` tensor-only ICT checkpoints, and RT-DETR initialization can use the pinned safetensors file. Scratch and pretrained architecture variants must reconstruct from the saved config.
- For resume, preserve the complete model directory, original config and data, compatible code and library versions, original pretrained inputs where applicable, and the verified checkpoint fingerprints. COCO training seeds each epoch and restores optimizer and scaler state. YOLO native EMA-based resume can follow a different trajectory from an uninterrupted run. This audit establishes artifact and settings checks, with no general bitwise reproducibility claim.
- Capture-time product inference requires either a zero-second state or an explicit `at-or-before-capture-v1` lookback. Fit the state only from eligible Train records and publish its exact payload. It records channel order, units, config, Train fingerprint, scaling and fill statistics. Positive capture-through-decision windows are offline-only for their declared decision time. It remains necessary to verify that measurements arrive by capture on the live acquisition path, including delayed or backdated deliveries.
- The five sensor channels are temperature, humidity, vibration, acceleration and noise. The index checks provider folders/stems, filename and capture timestamp, comparable strictly increasing clocks, and JSON/XLSX agreement on lengths, nulls and values. Live pairs require receipts binding sample and source IDs, original-image bytes, capture time and causal readings. Numerical image and sensor IDs can legitimately differ. Values of `defect_detected`, filenames, source IDs, boxes and absolute time stay outside model features. Real receipt generation, device clocks and availability at capture need validation.
- Product inputs use RGB and independently masked windows. Numeric zero is observed and imputed or padded values retain a false observation mask. Available encoders include observed-mean or statistics MLP, optional GRU over multiple observed timestamps, RGB grid, and pooled Faster R-CNN FPN. Fusion can average logits, concatenate embeddings or learn a gate. Targets are any-target presence or five independent canonical class presences from original boxes. Masked binary cross-entropy operates on usable rows of the selected branch. Missing modalities use eligible unimodal heads or abstain. Detached detector evidence remains spatial. The default real-data index has only one capture-time step per eligible paired view under its current window policy, so establish multi-step causal coverage before GRU experiments.
- Product checkpoints use `ict-multimodal-state-v1`, exact finite FP32 tensors, versioned encoder/architecture metadata and explicit per-branch weight declarations. The loader checks exact keys, shapes, dtypes, the frozen state and architecture fingerprints. Serving also pins the raw checkpoint SHA-256. A pooled FPN run needs the matching detector transform. Checkpoint publication requires hard links on the output filesystem. The product checkpoint is an inference state format. The product runner keeps optimizer, scheduler and RNG in a separate tensor-only epoch artifact and binds both files to the run's resume contract.

## Training and holdout policy

For this release, freeze model settings using Train or independently designated development groups inside Train. Any resampling and augmentation must use Train only. Freeze epoch budget, run list, thresholds and operating point before opening final Validation results. Record the assignment, cohort and artifact digests before the first approved fit.

The detector adapters perform optimizer updates only on Train. The COCO Validation pass runs without gradients and retains evaluation normalization. YOLO computes Validation fitness and the COCO adapters compute Validation loss to publish a `best.pt`; Validation therefore **does influence selection of the best checkpoint**. The integrated detector DAG and normal pilot workflow use that selected checkpoint for their reports. For a fixed-epoch frozen benchmark use standalone `ict evaluate --checkpoint last` and keep intermediate Validation metrics out of all decisions. If the requirement is zero Validation access during fitting, the current detector runners are **BLOCKED** for that interpretation. They perform a Validation pass each epoch. The product runner verifies the Train split before optimizer updates. It supports fixed epochs with Validation disabled or evaluated once at the final epoch. Per-epoch Validation and metric-based selection require explicit profile settings.

Keep internal Test under a separate access policy and out of fitting, configuration choices, checkpoint and threshold selection, calibration, pilots and reporting during development. The available Test revision is an internal same-source group holdout. Make any later scoring a separate approval after freezing run IDs, checkpoints, preprocessing, code, hardware, metrics and thresholds. The detector CLI requires an explicit holdout attestation, verifies the reference revision and rejects shared names or byte-identical images. The attestation does not establish session independence. Product comparison is currently Validation-only. This audit did not score real internal Test. Tests of holdout contracts use tiny synthetic data. External performance claims require separately collected, independently labeled production cohorts and a documented sampling design.

### Recommended detector order

1. Start with YOLO11n for the first feasibility pilot. Stage its private copy/cache on a measured volume, set explicit FP32 and one visible accelerator, and check that small boxes remain resolved at the planned image size.
2. Run Faster R-CNN FPN next as a two-stage reference and to establish the image encoder path for product experiments. Confirm TorchVision NMS and ROI Align forward/backward on the actual device.
3. Run RT-DETR R18 with its pinned runtime, query-compatible image size, and the same split, seed policy and Validation protocol. Record its backend-specific resize and query selection.
4. Establish one pinned pretrained baseline per model. Use Train-only development for photometric, geometry, balancing and combined ablations. Explicit `optimization: {}` provides a controlled no-augmentation/no-balancing baseline. Omitting the key preserves native YOLO augmentation. Policy proposals are seeded per sample, reject unsafe clipping and preserve background/label semantics. COCO uses lazy transforms and YOLO stages lossless private PNGs for controlled variants. Weighted and class-aware sampling draw a fixed Train cohort with replacement and may amplify source imbalance. Review unique draws and exposure by class and group. Validation and Test assignment stay fixed.

### Recommended sensor and fusion order

1. Audit the same approved revision with `ict multimodal audit`. Freeze a causal Train state, branch eligibility, feature order, target policy, thresholds and comparable paired Validation cohort. The runnable legacy CPU baseline is useful for a separately named experiment with its own preprocessing and comparison contract.
2. Plan sensor-only MLP and image-only RGB heads independently on eligible Train rows. Begin with the one-step sensor state and a simple RGB baseline. The runner uses RGB-grid image encoding. A trainable FPN arm still needs a separately pinned initialization and transform contract.
3. Compare fixed-weight late fusion, concatenation and gating on verified Train pairs. Each profile records branch training provenance. Report exact paired coverage and unimodal fallback coverage separately. Verify sufficient causal observations across groups before capture-time temporal experiments. A declared positive decision window supports a separate offline protocol.

## Frozen Validation evaluation

For detection, freeze one labeled COCO Validation set with the same image bytes, dimensions, boxes, class policy, score floor, threshold, IoU, cap, preprocessing and evaluation code for all detectors. Record backend-specific resize and postprocessing. The shared evaluator computes non-crowd, all-area COCO-style AP with 101 recall points, IoU 0.50–0.95 and a cap of 100 predictions per image and class. Class AP is null when ground truth is absent. Precision/recall/F1 use class-aware matching at the fixed operating point. The confusion matrix instead matches by IoU across predicted classes, with a background row and column. Reference parity against external `pycocotools` remains unverified here. Benchmark speed at batch one with common warmup and device/precision. Timing includes decode, preprocessing and postprocessing. Compare speed only on matching hardware and runtime conditions.

For product evaluation, use `FrozenValidation.from_audit` to bind eligible paired IDs, image and causal-sensor fingerprints, labels and input dimensions before inference. Supply exactly one successful matching record per sample and requested branch to `evaluate_products`. Fallback rows cannot satisfy the paired comparison. Product metrics are presence precision, recall, F1, AUROC and confusion counts per output. Unknown truth is counted and excluded for that output, and undefined metrics are null. AUROC uses uncalibrated ranking with half credit for ties. Use `DetectionProtocol` and `evaluate_detector_artifact` for trusted detector evidence on the same cohort. Compare like tasks with `compare_experiments`; keep box AP and product presence metrics in distinct reports.

Simulated and untrained product reports carry their status and prediction fingerprints with null metric fields. Pending and unscorable reports also carry no accuracy. Mock inspection records require review and identify the simulated scenario. Default real statistics exclude mock, untrained and unavailable product results. History can still show untrained product records and their labels. Statistics and CSV/dashboard detection counts are operational evidence counts. A trusted-trained status relies on the checkpoint producer’s declaration and trusted run metadata. A content digest alone cannot establish that fitting occurred. No performance result from fixtures supports a factory accuracy claim.
